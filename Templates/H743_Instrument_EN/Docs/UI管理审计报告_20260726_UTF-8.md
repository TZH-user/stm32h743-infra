## 1. 结论

### 1.1 总体判断

**有依据：**当前工程的 UI 目录分层基本合理，但运行时管理架构已经出现明显失衡。当前主要问题并非单个按钮回调，而是以下几类问题叠加：

1. `DisplayTask` 同时承担 LVGL、校准流程、ADC 采集、DAC 控制、QSPI 存储和串口 UI 命令执行。
2. UI 没有统一状态机，`MainTask`、`PhaseLockTask`、`CalibrationService` 和多个 Adapter 各自持有一部分状态。
3. 页面创建、绑定、导航和删除存在多条路径，触摸导航与串口导航行为不一致。
4. 一次分析完成与持续锁相输出没有在 UI 语义上分开，造成显示 `FINISHED` 后部分按钮仍然被禁用。
5. 当前存在会造成 UI 暂时停顿、触摸失效以及潜在永久卡死的直接代码路径。

### 1.2 架构评价

| 项目 | 评价 | 判断类型 |
| --- | --- | --- |
| CubeMX、业务、UI 目录分层 | 基本合理 | 有依据 |
| LVGL 单线程所有权 | 当前大体遵守 | 有依据 |
| UI 状态管理 | 不合理，状态源过于分散 | 有依据 |
| DisplayTask 职责 | 不合理，已经超出显示任务边界 | 有依据 |
| 页面生命周期 | 不统一，串口与触摸路径不一致 | 有依据 |
| Designer/Custom 页面管理 | 存在双重真源 | 有依据 |
| UI 自动化测试和运行诊断 | 明显不足 | 有依据 |

**经验判断：**当前目录结构可以保留并继续演进，但不建议继续在现有两个大型 Adapter 中追加零散条件。应先收敛状态模型、任务所有权和页面生命周期，再修复具体按钮。

## 3. 当前 UI 调用架构

```text
TouchTask
  -> GT9xx 软件 I2C
  -> 共享触摸快照
  -> LVGL indev read_cb

MainTask
  -> 一次采集与识别
  -> AppUiAdapter_SubmitAdcFrame()
  -> 成功后请求 PhaseLockTask 持续运行

PhaseLockTask
  -> 持续 ADC 跟踪
  -> DAC 输出
  -> g_app_phase_lock_status

SerialControlTask
  -> UiControlQueue
  -> DisplayTask 模拟页面加载或按钮点击

DisplayTask
  -> AppCalibrationService_Run()
  -> AppCalibrationBoardPort_Run()
  -> AppUiRemoteControl_Run()
  -> App_LvglRun()
       -> AppUiAdapter_Run()
            -> AppCalibrationUiAdapter_Run()
       -> lv_timer_handler()
```

当前最关键的问题是：硬件执行路径、存储路径和 LVGL 路径被放在同一个 `DisplayTask` 串行执行。

## 4. 高优先级问题

### P0-01：DisplayTask 中存在阻塞式 ADC、QSPI 和校准硬件操作

**判断类型：有依据。**

`APP/RTOS/app_display_task.c:36-44` 的循环顺序为：

```c
AppCalibrationService_Run();
AppCalibrationBoardPort_Run();
AppUiRemoteControl_Run();
App_LvglRun();
osDelay(5);
```

具体阻塞路径包括：

1. `APP/Calibration/app_calibration_board_port.c:395-429`
   - ADC 采集等待最长 `100 ms`；
   - 等待期间虽然调用 `osDelay(1U)`，但 DisplayTask 不会运行 LVGL。
2. `APP/Calibration/app_calibration_service.c:492-502`
   - 在 `PREPARE_SESSION` 状态中同步切继电器并开始存储会话。
3. `APP/Calibration/app_calibration_storage_port.c`
   - 会话头、测量点和结束记录都直接同步写入 QSPI；
   - 元数据或日志扇区切换时可能执行 `Erase4k`。
4. `APP/BoardFlash/app_board_flash.c:34-39`
   - Flash 互斥锁使用 `osWaitForever`。
5. `APP/BoardFlash/board_flash_w25q64.c`
   - 常规命令、写入和 4 KiB 擦除超时均可达到 `1000 ms`。

可能现象：

- 点击 START 后界面停止刷新；
- STOP、HOME 或触摸释放不能及时处理；
- Flash 操作期间页面看起来卡死；
- 外设异常时卡顿持续时间显著增加。

**结论：**这是当前最明确的 UI 卡顿根因之一，与 LVGL 本身是否死锁无关。

### P0-02：MainTask 高优先级忙等可饿死 DisplayTask

**判断类型：有依据。**

任务优先级：

| 任务 | 优先级 |
| --- | --- |
| `PhaseLockTask` | High |
| `MainTask` | AboveNormal |
| `DisplayTask` | Normal |

`APP/RTOS/app_main_task.c:470-475` 等待 ADC 帧时没有 `osDelay()`：

```c
while (!frame_acquired && !s_stop_requested
       && ((osKernelGetTickCount() - capture_start_tick)
           < capture_timeout_ticks))
{
    frame_acquired = AD9226_AcquireLatestFrame(&frame);
}
```

`SIGNAL_DETECT_CAPTURE_TIMEOUT_MS` 为 `100 ms`。

当 ADC DMA 帧没有及时到达时，AboveNormal 的 MainTask 会持续抢占 Normal 的 DisplayTask，导致 LVGL 和触摸处理暂停。

**结论：**这是调度层造成的确定性 UI 停顿风险。

### P1-01：UI 显示 FINISHED，但 PhaseLockTask 仍持续运行

**判断类型：有依据。**

`UI/Adapter/app_ui_adapter.c:503-526` 在投票结束后把 `analysis_state` 设置为 `FINISHED`。

但分析有效时，`APP/RTOS/app_main_task.c:538-541` 会请求 `PhaseLockTask` 启动持续锁相。

相位按钮使能条件位于 `UI/Adapter/app_ui_adapter.c:259-293`：

```c
bool phase_editable = !AppPhaseLockTask_IsRunning();
```

因此当前真实语义是：

```text
一次识别结束
  -> UI 显示 FINISHED
  -> 持续锁相和 DAC 输出开始
  -> 相位 +/- 按钮保持禁用
```

这直接解释了“任务已经完成，但部分按钮仍然不能按”。

需要区分的 UI 状态至少包括：

- `IDLE`
- `ANALYZING`
- `ANALYSIS_DONE`
- `TRACKING`
- `TRACKING_STOPPING`
- `CALIBRATING`
- `REVIEW`
- `ERROR`

### P1-02：Monitor RUN/STOP 没有完整按钮状态策略

**判断类型：有依据。**

`UI/Adapter/app_ui_adapter.c:153-195` 只为 RUN/STOP 注册事件，没有长期保存两个按钮指针，也没有按业务状态刷新 `LV_STATE_DISABLED`。

现状包括：

- RUN 在运行期间仍显示可点击；
- STOP 在空闲期间仍显示可点击；
- RUN 被拒绝时只把标题改为 `BUSY`；
- STOP 被拒绝时没有直接反馈；
- 视觉状态和业务状态不一致。

### P1-03：Calibration UI 回调普遍忽略业务返回值

**判断类型：有依据。**

`UI/Adapter/app_calibration_ui_adapter.c:235-347` 中多个调用直接转换为 `void`：

```c
(void)AppCalibrationService_SetSelection(...);
(void)AppCalibrationService_RequestStart(...);
(void)AppCalibrationService_RequestFinishSession();
(void)AppCalibrationService_RequestExit();
(void)AppCalibrationService_RequestConfirmCandidate();
```

影响：

- START 被拒绝时没有明确原因；
- STOP 失败后界面仍可能保持原样；
- 页面离开、确认、取消和应用失败缺少反馈；
- 用户无法区分“按钮没有回调”和“业务状态拒绝”。

### P1-04：串口 PAGE 后立即 TAP 可能丢失业务动作

**判断类型：有依据。**

`AppUiRemoteControl_Run()` 在 `App_LvglRun()` 之前执行，并且每轮最多处理 4 个命令。

如果队列连续包含：

```text
UI PAGE TEST
UI TAP CALSTART
```

则可能发生：

1. PAGE 创建并加载 Test 页面；
2. Calibration Adapter 还未扫描并绑定 START 回调；
3. TAP 找到按钮并发送 `LV_EVENT_CLICKED`；
4. 事件没有业务接收者；
5. 串口层仍可能将 LVGL 事件分发结果记录为 `OK`。

`APP/SerialControl/app_ui_remote_control.c:46-54` 当前把 `lv_obj_send_event()` 的返回值当成业务成功，不能证明 `AppCalibrationService_RequestStart()` 被接受。

### P1-05：串口创建页面缺少自动删除，可能泄漏 LVGL 对象

**判断类型：有依据。**

触摸导航使用 `lv_obj_add_screen_create_event()`。LVGL 内部会为新页面注册 `LV_EVENT_SCREEN_UNLOADED` 删除回调。

串口导航位于 `APP/SerialControl/app_ui_remote_control.c:57-93`：

```c
screen = screen_test_create();
lv_screen_load(screen);
```

该路径没有注册页面卸载删除回调。

反复执行串口 PAGE 命令可能使旧页面继续占用 LVGL heap。

当前 LVGL 配置：

- 固定 heap：`64 KiB`；
- `LV_USE_ASSERT_MALLOC = 1`；
- 默认 `LV_ASSERT_HANDLER` 为 `while(1)`。

**经验判断：**串口频繁切页可能造成 heap 碎片、分配失败并进入永久循环，表现为整机 UI 卡死。

### P1-06：动态页面刚打开时按钮可能暂时没有回调

**判断类型：有依据。**

Test 和 Calibration 页的 START/STOP 等回调由 `AppCalibrationUiAdapter_Run()` 在页面加载后查找并绑定。

但该函数被放在 `AppUiAdapter_Run()` 的 `50 ms` 轮询门限之后。

页面刚显示时可能出现：

- 控件已经可见；
- Adapter 尚未绑定；
- 用户快速点击没有效果；
- 如果 DisplayTask 同时被 ADC/QSPI 阻塞，未绑定窗口进一步扩大。

### P1-07：Calibration/Test 页面逻辑错误依赖 Monitor Adapter 初始化

**判断类型：有依据。**

`AppCalibrationUiAdapter_Run()` 只从 `AppUiAdapter_Run()` 内部调用，而 `AppUiAdapter_Run()` 开头存在：

```c
if (!s_initialized)
{
    return;
}
```

`s_initialized` 又来自 Monitor 页面图表、下拉框、标题和序列绑定结果。

因此，只要 Monitor 模板对象名变更、Chart 序列缺失或初始绑定失败，Test/Calibration 页面逻辑也会全部停止运行。

这是不合理的跨页面耦合。

### P1-08：触摸读取错误可能留下永久 PRESSED 状态

**判断类型：推测，有直接代码风险，但尚未真机故障注入。**

`BSP/Touch/app_touch_gt9xx.c:226-233` 在 I2C 读取失败或没有新数据时直接返回，不会清除旧的 `g_touch_state`。

如果旧状态为 pressed，而释放帧读取失败，LVGL 可能持续看到 pressed，导致：

- release/click 序列不完整；
- 后续按钮无响应；
- 用户感觉 UI 卡住。

当前还缺少：

- 连续读取失败计数；
- 最后有效触摸时间；
- stale pressed 超时释放；
- 软件 I2C 总线恢复；
- 错误状态调试快照。

### P1-09：LVGL heap 无实时诊断，分配失败会直接死循环

**判断类型：经验判断，需运行数据确认。**

当前配置：

- LVGL heap：`64 KiB`；
- Monitor 为永久页面；
- Test 生成代码约有 90 余个对象创建点；
- Calibration 生成代码约有 70 余个对象创建点；
- 页面创建时新页面必须先分配完成，旧页面之后才卸载；
- 未启用 `lv_mem_monitor()`、最大连续空闲块或碎片率诊断；
- malloc 断言失败后进入 `while(1)`。

现有 UI 管理规范也明确记录：当前仍没有新页面的 LVGL heap 峰值、碎片率和连续切页数据。

## 5. 中低优先级问题

### P2-01：Control 和 System 存在外观可用但无逻辑的按钮

**判断类型：有依据。**

Control 页面当前没有业务事件的按钮：

- `Select`
- `Select`
- `Edit`
- `APPLY`

System 页面当前没有业务事件的按钮：

- `Touch Test`
- `Display Test`
- `Memory Status`

这些控件应选择其一：

1. 实现业务逻辑；
2. 明确添加 disabled 状态；
3. 显示 `NOT IMPLEMENTED`；
4. 在正式版本中隐藏。

不能保持普通可操作按钮样式。

### P2-02：UI 状态源过于分散

**判断类型：有依据。**

当前 UI 状态分别来自：

- `analysis_state` Subject；
- `AppMain` 的多个 volatile 标志；
- `g_app_phase_lock_status`；
- `g_app_dac_output_status`；
- `AppCalibrationSnapshot`；
- `AppUiAdapter` 静态绑定状态；
- `AppCalibrationUiAdapter` 静态页面状态。

缺少统一的：

```c
AppUiState
AppUiCommand
AppUiCommandResult
AppUiButtonPolicy
```

这是按钮恢复不完整和状态显示互相覆盖的架构根因。

### P2-03：Designer 与 Custom 仍然是双重页面真源

**判断类型：有依据。**

当前 Monitor：

1. `signal_separation_ui_init()` 先创建 Designer Monitor；
2. `UI/pages/app_lvgl_ui.c` 删除该页面；
3. 再通过 `AppInstrumentScreen_Create()` 创建 Custom Monitor。

后果：

- LVGL Pro 预览不一定等于真机；
- 修改 XML 不一定改变真机；
- 修改 Custom 不会同步预览；
- 两套布局必须人工保持一致。

### P2-04：控件绑定仍然依赖运行时递归搜索和文字匹配

**判断类型：有依据。**

`app_calibration_ui_adapter.c` 同时使用：

- 对象名递归查找；
- 按标签文本查找 BACK/HOME；
- 按控件类型和出现顺序查找进度条；
- 按固定文字查找 APPLY 标签。

风险：

- Designer 改名后业务逻辑静默失效；
- 文案调整或本地化后找不到按钮；
- 页面新增同名文字后可能绑定错误对象；
- 绑定失败没有统一错误报告。

### P2-05：UI 控制路径没有落实既有命令队列设计

**判断类型：有依据。**

工程 UI 管理规范建议：

```text
LVGL event
  -> AppUiCommand
  -> RTOS 消息队列
  -> 业务任务执行
  -> AppUiStatus/AppUiCommandResult
  -> UI 回显
```

当前实际实现仍是：

- Monitor 按钮直接调用 `AppMain_RequestStart/Stop()`；
- Calibration 按钮直接调用 `AppCalibrationService_*()`；
- 串口控制通过模拟按钮点击间接触发业务。

命令没有请求序号、处理结果、拒绝原因和完成通知。

### P2-06：当前工程文档已经出现架构描述滞后

**判断类型：有依据。**

示例：

- 旧 UI 管理规范仍描述生成页面内部直接跳转 Custom 的历史方案；
- 当前代码已经改为在 `app_lvgl_ui.c` 中删除生成 Monitor 后创建 Custom Monitor；
- `Docs/当前主线索引_UTF-8.md` 仍把 UI 描述为只读快照，但当前 UI 已经直接控制 Main、PhaseLock 和 Calibration 服务。

这会导致后续开发者或 AI 根据过期文档修改错误文件。

### P2-07：缺少 UI 状态机与页面生命周期自动化测试

**判断类型：有依据。**

CodeGraph 对 `AppUiAdapter_Run()`、相位按钮、页面绑定和按钮策略未发现覆盖测试。

当前主机测试主要覆盖 CalibrationCore 算法，没有覆盖：

- `READY -> START`；
- `SESSION_ACTIVE -> STOP`；
- `REVIEW -> START`；
- `FINISHED -> TRACKING`；
- `TRACKING -> STOP -> IDLE`；
- 页面进入和离开时资源独占；
- 串口 `PAGE + TAP` 快速序列；
- 连续切页对象是否释放；
- 触摸读取错误后的自动释放。

## 7. 文件结构评估

### 7.1 建议保留的结构

以下目录边界方向正确：

| 目录 | 建议职责 |
| --- | --- |
| `UI/Designer` | XML、组件、样式和自动生成页面 |
| `UI/Custom` | LVGL Pro 无法稳定表达的自定义控件行为 |
| `UI/Port` | 显示、触摸、Cache 和 framebuffer 适配 |
| `UI/Adapter` | 页面 View 与统一 UI Model 的绑定 |
| `UI/pages` | UI 启动、Page Manager 和页面注册 |
| `APP/RTOS` | UI、校准、采集和输出任务入口 |
| `APP/Calibration` | 校准业务服务和 STM32 板级 Port |
| `CalibrationCore` | 不依赖 HAL/RTOS/LVGL 的纯算法 |

### 7.2 建议调整的所有权

推荐目标：

```text
DisplayTask
  -> 只运行 LVGL、页面控制器和轻量 UI Model 刷新

CalibrationWorkerTask
  -> 继电器、ADC、DAC、QSPI、校准状态机

MainTask
  -> 一次分析，不进行高优先级忙等

PhaseLockTask
  -> 持续锁相和 DAC 输出

AppUiController
  -> 接收事件、投递命令、维护统一状态和按钮策略

AppUiPageManager
  -> 统一页面创建、加载、离开、销毁和 Adapter 生命周期
```

## 8. 推荐整改顺序

### 第一阶段：先处理卡死路径

1. 将 Calibration BoardPort 和 QSPI 存储移出 DisplayTask。
2. 将 ADC 等待改为信号量、线程标志或至少有界让出 CPU 的等待。
3. 增加 DisplayTask 循环最大耗时、最后运行 tick 和超时计数。
4. 增加 LVGL heap 使用量、最大连续空闲块和碎片率诊断。
5. 增加触摸读取错误、最后成功帧时间和 stale pressed 超时释放。

### 第二阶段：统一状态与按钮策略

1. 建立单一 `AppUiState`。
2. 建立 `AppUiCommand` 和 `AppUiCommandResult`。
3. 将所有按钮使能条件集中到一张状态策略表。
4. 将 `FINISHED` 改为能区分分析完成和持续跟踪的状态。
5. RUN、STOP、Phase、START、HOME 等全部由统一 Controller 管理。

### 第三阶段：统一页面生命周期

1. 建立 `AppUiPageManager`。
2. 触摸和串口页面切换都调用同一入口。
3. 禁止串口模块直接调用 `screen_*_create()` 和 `lv_screen_load()`。
4. 页面绑定在加载完成时立即执行，不依赖 50 ms 轮询偶然命中。
5. 页面离开统一释放业务会话、Adapter 指针和动态对象。

### 第四阶段：收敛 UI 真源

1. Monitor 页面结构逐步迁回 Designer XML。
2. Custom 只保留无法生成的行为和组件扩展。
3. 为所有业务控件建立稳定对象名契约。
4. 绑定失败必须产生诊断，不允许静默返回。

### 第五阶段：补测试

至少增加以下测试矩阵：

- Monitor RUN/STOP/Phase 状态矩阵；
- Test START/STOP/REVIEW 重测；
- Calibration 未实现项目硬门禁；
- 页面快速进入、退出和交叉切换；
- 串口 PAGE 与 TAP 连续命令；
- 连续切页 100 次 heap 稳定性；
- ADC timeout 和 QSPI timeout 时 UI 心跳；
- 触摸 I2C 错误后的自动释放。

## 9. 最终接管建议

**有依据：**当前最需要优先解决的五项是：

1. DisplayTask 阻塞式硬件和存储操作；
2. MainTask 高优先级忙等；
3. 一次分析与持续跟踪状态混淆；
4. 串口页面生命周期和虚假成功反馈；
5. 缺少统一 UI 状态机和按钮策略。

**经验判断：**如果不先解决上述架构问题，继续在现有 Adapter 中增加 `if`、手动增删 `LV_STATE_DISABLED` 或补单个事件回调，只会暂时掩盖现象，后续仍会反复出现：

- 任务结束后按钮状态错误；
- 页面刚打开时按钮无响应；
- 串口报告 OK 但业务未执行；
- 校准或 Flash 操作期间 UI 卡顿；
- 长时间切页后永久卡死。

建议下一阶段以“统一状态模型 + 拆出 CalibrationWorkerTask + 统一 Page Manager”为主线，不再继续向当前 DisplayTask 和两个大型 Adapter 堆叠职责。
